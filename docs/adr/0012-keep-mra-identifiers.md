# 0012. MRA に由来する識別子は MRA の表記のまま保持する

- ステータス：承認
- 日付：2026-11-01

## コンテキスト

MRA は、状態を表す値（enum）や構造化された値の要素に、`allStop`、`upperCenter`、`noData` のような lowerCamelCase の識別子を付けている。数字で始まるもの（`1stRinsing`、`200WOrMore` など）もある。

利用する側は、それぞれ別の命名規則を求めることがある。snake_case を求めるものも、camelCase や MRA の表記そのものを求めるものもある。lowerCamelCase から snake_case への変換は情報を失う（`ACMode` は `a_c_mode` になり、元に戻せない）。pyhems が特定の規則に変換すると、別の規則を求める利用者は元の識別子を取り出せない。

識別子をすべて Python の列挙型にする方法も検討した。しかし、次の理由で採用しない。

- 定義データの enum の識別子は 458 種類あり（enum を持つ非二値の定義は 220 件）、MRA の改訂で増減する。列挙型の構成が MRA の版に引きずられ、改訂のたびに API が変わる。
- 同じ識別子でも、プロパティによって意味が異なる。1 つの列挙型にまとめても意味を表せない。
- 数字で始まる識別子があり、列挙型のメンバー名にするには別の名前を付ける必要がある。
- 利用する側の多くは定義データを汎用的に扱い、個々の識別子を定数として参照しない。

## 決定

- MRA に由来する識別子は、MRA の表記のまま保持する。対象は、`EnumValue.key`、構造化された値の要素の識別子、構造化された値を解釈した結果として返す状態の識別子である。
- `custom_definitions.yaml` で追加する識別子も、書かれた表記のまま保持する。
- pyhems が自分で定める識別子は snake_case とする。対象は、二値に正規化した `true`/`false`、`level_N`、設置場所のキー、`Quantity`・`ValueKind`・`Indication` などの値である。
- 識別子を別の命名規則に変換する処理は、利用する側の責務とする。

## 結果

- 利用する側は、元の MRA の識別子を使うことも、必要な規則に変換することもできる。
- 命名規則の変換が必要な利用者は、変換を 1 か所にまとめ、送信する値と表示する値の両方に同じ変換を適用する必要がある。
- MRA の改訂で識別子が変わっても、pyhems の API の形は変わらない。
