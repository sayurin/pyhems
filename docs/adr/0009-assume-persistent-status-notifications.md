# 0009. INF と INFC は継続して受信できると仮定する

- ステータス：承認
- 日付：2026-10-31

## コンテキスト

ECHONET Lite では、状態変化時アナウンスプロパティマップ（`0x9D`）に載っている EPC について、機器が状態の変化をプロパティ値通知（ESV `0x73` INF、または `0x74` INFC）で知らせる。

一方、プロパティ値通知要求（ESV `0x63` INF_REQ）と、その後に通知が継続して届くかどうかの関係は、仕様で明確に定められていない。`0x63` を送ることで通知が始まるのか、`0x63` を送らなくても通知が届くのか、`0x63` への応答が一時的な値の通知にすぎないのかは、仕様からは判断できない。

pyhems は setup のときに、監視対象の EPC のうち `0x9D` に載っているものについて `0x63` を 1 回送り、`0x73`（INF）または `0x53`（INF_SNA）の応答を待っている。

## 決定

- `0x63` に対して `0x73` で応答があった EPC は、以後も INF または INFC を**継続して受信できる**と仮定する。
  - これらの EPC は、定期ポーリングの対象から外す。
  - `0x63` を再送したり、定期的に送り直したりはしない。
- `0x53` で拒否された EPC と、応答に含まれなかった EPC、タイムアウトした EPC は、引き続き定期ポーリングで取得する。

## 結果

- 通知に任せる EPC はポーリングしないので、機器への GET が減る。
- マルチキャストの通知が失われた場合や、機器が通知を止めた場合は、次に状態が変化するまで値が古いまま残る。
- これまでの運用では、この仮定による実用上の問題は確認されていない。問題が報告されたら、ポーリングとの併用などを検討してこの ADR を見直す。
