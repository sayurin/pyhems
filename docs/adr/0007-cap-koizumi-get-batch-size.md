# 0007. コイズミの 0x0290 と 0x02A3 では 1 回の GET の EPC 数を制限する

- ステータス：承認
- 日付：2026-10-25

## コンテキスト

[issue #123](https://github.com/sayurin/hems_echonet_lite/issues/123) で報告された機器構成は次のとおり。

- 機器：コイズミ（メーカーコード `0x0000E8`）の Smart Bridge AE54355E。
- 配下の照明：一般照明（`0x0290`）の 11 インスタンス（`0x029001`〜`0x02900B`）。
- AE54355E 自身：`0x02A301` として応答する。

この機器は、一度に多くの EPC を要求すると、0x72 Get_Res も 0x52 Get_SNA も返さない。
ADR-0004 の半減探索を導入してからの観測結果は次のとおり。

| 機器オブジェクト | 応答がなかった要求 | 半減後の要求 | 半減後の応答 |
|---|---|---|---|
| `0x0290` | 27 EPC | 14 EPC と 13 EPC | 応答あり |
| `0x02A3` | 17 EPC | 9 EPC と 8 EPC | 応答あり |

1 回目の半減で応答が得られるので、正常に動作する。ただし、インスタンスごとに最初の要求で 30 秒のタイムアウトを待つ。このため、12 個の機器オブジェクトの setup に約 6 分かかる。

上限の正確な値は分からない。`0x0290` は 14〜26、`0x02A3` は 9〜16 の間にある。これ以上の値を探るには、報告者に追加の試行を求める必要がある。

## 決定

- `get_batch_policy` に、1 回の GET に含める EPC 数の上限（`max_batch_size`）を加える。
- メーカーコード `0x0000E8` に次の上限を設定する。値は、半減後に応答が得られた EPC 数である。
  - デバイスクラス `0x0290`：14。
  - デバイスクラス `0x02A3`：9。
- この上限は、ADR-0001 で学習した同時応答数の上限とは別に持つ。実際の送信には、小さい方の値を使う。
- setup、定期ポーリング、即時ポーリング、公開 GET API のどの経路でも、メーカーとクラスが該当すれば同じ上限を守る。
- setup の最初の要求も、この上限で分割する。分割した要求に有効な応答があったら、ADR-0001 に従ってその EPC 数を同時応答数の上限として記録する。この上限で送っても応答がなければ、ADR-0004 に従って半減する。
- 製品コードを返さない機器オブジェクトがあるので、製品コードでは絞り込まない。

## 結果

- AE54355E 配下の機器オブジェクトは、setup の最初の要求からタイムアウトせずに応答を得られる。setup の時間は 1 機器オブジェクトあたり 30 秒以上短くなる。
- 上限は確定値ではない。実際の上限より小さい場合は、GET の回数が必要以上に増える。ただし、`0x0290` の取得対象（現在 27 EPC）は 2 回の要求で取得できる。
- 同じメーカーとクラスの他の機種にも、同じ上限が適用される。他機種の上限がこれより大きくても、GET が多く分割されるだけで、取得には影響しない。
