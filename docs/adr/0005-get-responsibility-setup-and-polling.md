# 0005. 同時応答数の探索は setup で行い、ポーリングは既知の値で分割する

- ステータス：承認
- 日付：2026-10-24

## コンテキスト

pyhems の GET には 2 つの用途がある。

1. **初期取得（setup）**：機器を見つけたときに、プロパティマップと監視対象の EPC を取得する。
2. **定期ポーリング**：通知（INF）では届かない EPC を一定の間隔で取得する。

これまでは、どちらの用途も「同時応答数の上限を超えたときの分割」と「上限の学習」を、それぞれ別々に実装していた。具体的には、要求数より少ない OPC の応答、すべてが PDC=0 の応答（ADR-0001）、そして残りの EPC の分割である。

二重に実装していたせいで、両者の挙動が少しずつ食い違っていた。加えて、ポーリング側は分割の途中経過を保持するために多くの状態を持つ必要があった。

ただし、両者の性質は次のように異なる。

- setup の時点では上限が分かっていないので、探る必要がある（ADR-0001、ADR-0004）。
- ポーリングは setup の後に行われるので、上限は分かっている。また、ポーリングは周期的に実行されるので、1 回失敗しても次の周期で取り直せる。

機器ごとの組み合わせ制約（`get_batch_policy`、ADR-0003 の 0xB3 と 0xB7 の併記禁止）は、どちらの用途でも守る必要がある。

## 決定

- **上限の探索は setup だけで行う。**
  - 分割、上限の学習、省略された EPC の追加取得は、setup 用の GET 処理にまとめる。同一要求のリトライはしない（ADR-0004）。
  - ここで学習した上限は、機器オブジェクトごとの状態として `HemsClient` だけが持つ。
- **ポーリングは探索しない。**
  - 送る EPC の分割は、組み合わせ制約と既知の上限を `take_first_batch` に与えて決める。これは setup と共通の計画関数である。
  - タイムアウトしたり一部の EPC が欠けたりしても、その周期の中で再送や再分割はしない。次の周期に任せる。
  - 失敗した周期は、生存確認とバックオフのために失敗として数える。
- ポーラーは送りっぱなしの送信と応答イベントによる進行を維持する。待機する GET タスク方式には変更しない。
- 送信計画（`take_first_batch`）は setup とポーリングで共通にする。違いは、計画どおりに送った結果が思わしくなかったときに探索や追加取得をするかどうか、だけである。

## 結果

- 上限を学習する処理が 1 か所にまとまる。ポーリングで持つ状態は、分割中の残りの EPC と送信予定の管理だけになる。
- ポーリングの途中で機器の上限が変わった場合（ファームウェア更新などで下がった場合）、ポーリング側では上限を学び直さない。タイムアウトや部分応答として観測できても、取得の改善には setup のやり直しが必要である。値の取得失敗と機器の無応答は区別する。
- 「全インスタンス宛て（インスタンスコード 0x00）の GET で、同じクラスのインスタンスにまとめて問い合わせる」方式は、リクエストと応答の対応関係が大きく変わる。そのため本 ADR の範囲外とし、別途扱う。
- setup の並列化も本 ADR の範囲外とし、別途扱う。
